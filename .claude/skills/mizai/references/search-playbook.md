# 新規性検索プレイブック(実行時参照用)

完全版の方法論: docs/03-verification.md。
本書は Phase 4(敵対的検証)での存在検索・墓場検索のクエリ設計手引き。

## 大原則

1. **名前で探すな**。名前のないものは名前で見つからない。候補の**機能**で探す
2. **検索0件は不存在の証明ではない**。「n クエリで反例なし(暫定)」とだけ言える
3. **全クエリをログせよ**。新規性判定の本体は判定語ではなく検索ログである
4. **見つけたくないものを探せ**。Phase 4 の任務は候補を殺すことである。生かす証拠ではなく殺す証拠を探す

## 存在検索(4a)のクエリ設計

候補1件につき、**同義語3系統×各2クエリ以上**(最低6クエリ)。

**早期打ち切り規則**: 実質同一の現行製品・手法を**2系統以上のクエリで確認**したら、残りの存在検索は打ち切ってよい(判定=既存、棄却ログへ)。任務は殺すことであり、死体の確認に儀式は要らない。1系統のみのヒットでは打ち切らない(同名別機能の誤認があるため)。

### 系統1: 機能+制約

一行仕様を「動詞+目的語」に分解し、制約語を足す。

- 形: `<対象> <機能動詞> <方式|制約>` / `<function words> device|system|method`
- 例(候補「排尿予兆の超音波検知」): `膀胱 超音波 センサー ウェアラブル` / `bladder ultrasound wearable sensor`

### 系統2: 実務者語彙

その分野の実務者・当事者が使うであろう語彙に翻訳する(学術語と生活語の両方)。

- 例: `トイレ 予測 介護 デバイス` / `incontinence prediction device`

### 系統3: 否定形・嘆き形

「なぜ無いのか」と嘆く声は、存在すれば必ず先行例情報を引き寄せている。

- 形: `なぜ 〜 がない` / `why is there no <function>` / `<function> alternatives`

### 必須の1系統: 特許

- `site:patents.google.com <機能語(英語)>` を最低1クエリ含める
- ヒットした特許は「最接近先行例」の第一候補。請求項まで読まなくてよいが、要約との差分は記録する

## 墓場検索(4b)のクエリ設計

- 形: `<候補の機能語> 撤退|終了|failed|discontinued|shut down|post-mortem`
- スタートアップ墓場: `<機能語> startup failed` / `<機能語> なぜ失敗`
- 死骸が見つかったら**死因を一文で特定**し、「死因は現在のイネーブラで解消されているか」を判定する
  - 解消の証拠あり → 候補は生存(むしろ強くなる: 需要は実証済み)。カードのイネーブラ欄に死因解消の出典を書く
  - 解消の証拠なし → 棄却。棄却ログに死骸のURLと死因を書く

## ヒットの解釈規約

| 発見物 | 判定 | 処理 |
|---|---|---|
| 実質同一の現行製品・手法 | 既存 | 棄却(棄却ログへ) |
| 近いが明確な差分のある先行例 | 差分新規 | カード化可。差分を新規性ログに明記 |
| 同案の死骸(死因解消済み) | 暫定新規(D型) | カード化。イネーブラ欄を強化 |
| 同案の死骸(死因存続) | 棄却 | 棄却ログへ |
| 学術提案のみで実装なし | 差分新規 | カード化可。「実装の未在」として診断を書き直す |
| n クエリで反例なし | 暫定新規 | カード化。ログにクエリ全列挙 |

境界事例の規則: 商用品が皆無で研究文献が1〜2件のみの場合は**差分新規**とする(その文献が最接近先行例。「差分=実装と製品化の未在」と書く)。「暫定新規」は研究・製品とも反例ゼロの場合に限る。

## ログの書式(04-redteam.md に記録)

```
### <候補ID> 存在検索
- Q1 `<クエリ>` → <ヒット概要 or 反例なし> <URL(あれば)>
- Q2 ...(最低6行)
- 特許: `site:patents.google.com ...` → ...
- 最接近先行例: <名称+URL> / 差分: <1文>
- 判定: [暫定新規|差分新規|既存]
### <候補ID> 墓場検索
- Q: `<クエリ>` → <死骸の有無>
- 死因: <1文> / 死因解消: [あり(URL)|なし|該当なし]
```
